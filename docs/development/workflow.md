# 开发与评审流程

新增组件、修复行为与优化效果都按受影响的链路推进。文案或格式修改只执行相关文档检查，不要求重新分析原厂。

## 官方 1:1 对齐

**新增 COUI 能力必须以官方实现为基准，效果至少达到 1:1，尽可能采用相同的算法、参数语义、执行顺序和状态转换。** “看起来相近”不能作为验收标准。这里的官方指选定版本的 COUI/Oplus 原厂实现；Demo 中的 M3 控件按相应 AndroidX 官方接口与规范装配。

优先使用 Android/Compose 公开 GPU 接口承载相同计算，不依赖 OEM 私有 SDK、私有 HWUI 符号或厂商 SO。遇到公开 API 无法表达的路径，先记录具体差异及对效果的影响，再提出方案；未获当前任务授权，不自行换算法、削减交互或声称完成 1:1。优化也受此约束，不能以层数减少代替效果或性能证据。

不能因为名称同为 blur 或 spring 就用另一种算法替换；不能用均匀模糊加渐变代替已确认的位置可变卷积，或用连续公式替换已确认的离散查表。复用现有材质、按压或动画组件，也需要核对它在新场景中的参数、合成位置和取消规则。

现有实现包含用户已批准的特化，例如菜单组合描边、顶栏强度/收起速度和宿主 G2 形状。它们是已有约束，不因重新对照原厂就自动撤销。对应 Note 持有理由和范围；新增差异必须单独说明和评审，不得将特化表述为官方默认。

## 基础效果复用

**新增组件前，必须检查[效果目录](../effects/README.md)、对应实现和已有消费者，先确定复用方案，再写组件。** 模糊、材质混色、轮廓与内晕、阴影、跟手光、触摸动效和融合均已有基础实现或组合入口。

1. 将目标原厂分支与现有实现对照，核对算法、单位、坐标、合成位置、状态与资源生命周期。现有实现满足目标时必须复用，通过参数、所属 Defaults 和合成顺序完成组件装配。
2. 新组件实现自己的布局、语义和局部状态，不因组件不同而复制 Shader、模糊核、混色、轮廓光或阴影算法。复用已有后端，也不增加只转发参数的包装层。
3. 现有能力不足时，先评估对所属公共 effect 做最小扩展，并检查已有消费者；不为尚未出现的用途增加抽象、开关或参数。
4. 只有确认算法分支或执行语义无法复用时，才新增实现。在对应 Note 与 PR 中说明检查过的候选、实际缺口、原厂依据及新实现归属，供评审核对。

复用以原厂行为一致为前提。渐进 Gaussian、菜单 Fast Kawase 和均匀模糊各自选择对应实现，不能为复用而替换算法。复用代码不等于跨节点共享可变 renderer；资源要求见[背景采样](../effects/backdrop.md#资源与失败处理)。

## 开发与评审流程

### 1. 固定目标与证据

先写清目标页面、控件、操作和状态，再确定实际使用的组件、主题覆盖及分支。按[复刻指南](replication-guide.md#2-从系统页面到实际消费者)核对对应 APK、framework 或 native 库的版本、构建标识或哈希。优先读官方源码；使用反编译结果时，关键分支须交叉核对。

检索现有 Note，将结论分为原厂行为、公开平台适配和项目主动特化。只记录与本次行为有关的材料、符号和证据缺口；不要把整包导出、本机目录或厂商二进制加入运行依赖。

### 2. 对照行为，而不只对照参数

对含输入、滚动或动画的组件，在对应 Note 中记录主要操作与退出路径：前置状态、原厂入口、状态修改、移植入口及差异。继承的基类、父容器分发、回调和公共辅助函数都属于调用链，不能只检查目标类。

至少区分受影响的正常完成、中途反向、未达到拖动阈值的 UP、CANCEL、父容器接管和节点移除。记录位置、速度、目标及积分临时状态由谁修改，不能将同名“回弹”或“取消”合并成一种行为。绘制遮罩、命中范围、点击、按压和点触光也要分别核对。

### 3. 实现完整链路

按[基础效果复用](#基础效果复用)确认所用后端与必要扩展，再实现组件装配。

先还原数据与状态转换，再选择公开承载。单位、坐标、采样网格、合成顺序、预乘 alpha、覆盖率、量化和资源生命周期的检查方法见[复刻指南](replication-guide.md#4-移植前要写清的边界)。

所有会停止旧动画或接管手势的入口，都要有对应的完成、取消和释放路径。共享入口的调整只作用于需要的消费者，保留其他调用方已有行为；不增加没有职责收益的公共状态机或只转发参数的包装层。

### 4. 实现完成后做双向核查

完成整条链路后再做最终代码评审。评审者重新读原厂关键入口和当前生产代码，不以 PR 摘要、注释或已有检查结果代替：

- **原厂 → 移植**：逐项检查实际使用的分支、状态更新和退出处理，找遗漏。
- **移植 → 原厂**：检查新增的重置、裁剪、合成和回调是否有原厂依据，或属于已批准适配，找多做和改错。

评审范围包含调用方及被复用的公共实现，不限于 diff 行。主实现者必须亲自复核核心代码；独立审查可补充证据，不能替代核心理解。发现差异后修复，或按既有授权记录适配；无法确认的部分保留待验证状态。

评审同时检查组件中是否重复实现已有基础效果；新增后端须有无法复用的具体依据，公共 effect 的扩展须覆盖已受影响的消费者。

### 5. 用能暴露差异的输入验证，再交付 PR

先选择能区分原厂与移植行为的最小输入序列，检查中间状态、收尾及重新进入，不只检查动画最终停止。能执行原库时使用相同输入对照；只能做静态核对或替身检查时，明确覆盖范围。增加大量同类参数组合，不能替代遗漏的事件路径，也不要求为每次研究保留一套测试框架。

设备验收使用同一原厂基准，并对齐尺寸、density、深浅色、字体和输入序列。覆盖受影响的静止、按压、拖动、反向、取消、隐藏/恢复、RTL、键盘及无障碍；视觉检查包含动画中段，性能结论需要可复现的设备数据。执行权限按 AGENTS，不因验收要求自行运行构建或设备操作。

PR 按[模板](../../.github/pull_request_template.md)列出原厂依据、主要路径对照、已处理差异、真实检查结果和待验收项。结构检查通过、数值收敛和参数一致都不能单独证明原厂等价。

## 同步使用文档

实现完成后，按[文档维护规则](documentation.md)更新受影响的 component、effect、兼容要求和示例。使用文档与实现进入同一个 PR；Note 记录理由，Demo 展示装配，二者都不能替代使用说明。

新增或修改公共效果时，检查使用该效果的所有组件和 Demo；修复组件时，检查其共享算法与已知消费者。更新相关语义，不顺带扩展展示范围。

## 决定记录

使用仓库内的 [write-notes-like-deepseek Skill](../../.agents/skills/write-notes-like-deepseek/SKILL.md)。不依赖某位开发者的全局安装。行为、架构、跨文件契约、开发流程、验证策略或数据格式改变时必须写或更新 Note；纯格式、无歧义重命名和不改行为的局部机械修改不新建 Note。

动手前搜索活跃决定：

```sh
rg --hidden --glob '!.agents/notes/archived/**' '组件名|机制名' .agents/notes/
```

同一决定的路径、符号等事实就地更新。理由翻转则新建并互链，不覆盖旧理由。新建时将命中项分类为无关、部分重叠、完全吸收或过时提案，并记录处理结果。只建立实际使用的生命周期/分类目录，不建立 INDEX。

Note 与实现同一个 PR。正文说明问题、当前决定、真实备选、代价和验证限制；引用当前源码位置，避免复制可变参数。尚未实施用 proposed，落地后移入 implemented 并同步状态，不能保留已完成的计划正文。用户当前授权和仓库执行规则优先于 Skill 的通用确认流程，不额外增加确认门。

校验命令与执行结果要求见[验证与评审](validation.md)。归档检查整个分支时，使用目标分支共同基点作为 AGENT_NOTE_ARCHIVE_BASE_REF；PR CI 使用 PR 的 base SHA。

## 提交 PR

开发使用功能分支，自动代理默认使用 codex/ 前缀。按[贡献指南](../../CONTRIBUTING.md)和 [PR 模板](../../.github/pull_request_template.md)交付；Git 操作与设备操作遵守 [AGENTS.md](../../AGENTS.md) 的授权范围。

PR 说明最终行为、原厂目标与主要路径对照、已处理差异、公开 API 和迁移影响、使用文档、Note、真实检查结果与待验收项。只改变流程或文档时，说明原厂对照不适用的原因。

历史流程取舍见[开发与 PR 决定](../../.agents/notes/implemented/process/2026-10-23-developer-guide-and-pr-notes.md)。
